Purpose

A synchronous request/reply service (KPN EAI service 1046 'UpsertContact', contract 0426). It receives a contact person, first has it validated by CDCAdapter (ValidateContact, contract 0425) and, only if the validation reports no warnings, no errors and status 0, creates or updates the contact in UCM through UCMAdapter (UpsertContact, contract 0430). The caller receives the outcome: success with UCM's returned contact data, or the validation or UCM result explaining why the contact was not stored.

Business context

It lets front-end CRM consumers maintain contact persons in the customer master (UCM) while enforcing data-quality validation, with the possibility of overriding validation warnings. The callers are not identified in the export. CDCAdapter's underlying system is not named in the export. The UCM data written here is later published as contact events, which crm-upsert-contact-pub applies to SFA; that link is inferred from the 0429 schema namespace, not from code in this flow.

Summary

UpsertContact is the service front-end applications use to create or update a contact person in UCM. Each request is first checked by a validation service (CDCAdapter), which reports warnings and errors for the person and for each address. Only a clean result lets the contact through to UCM. The caller can mark the contact, or individual addresses, with an override flag to accept warnings. Errors cannot be overridden.

The caller always receives a reply. On success, it contains the contact as stored by UCM. If validation stops the contact, the reply carries the validation status and details. If UCM rejects it, the reply carries UCM's status. Only technical failures (an unreadable request, a timeout or an unexpected error) produce a 'Technical Error' reply and, after a successful parse, an e-mail to integration support.

The business logic is moderate: two calls in sequence, some decisions and a counting rule. The mappings are large but mostly straight copies. As with the rest of CRMServices, the main obstacles are the TIBCO Rendezvous transport, which Boomi cannot use, and the missing header schemas. One counting rule also behaves in a way that may be a defect, and it needs a business decision before it is copied.

Key points

  • Two back-end calls in sequence: CDC ValidateContact, then UCM UpsertContact; each times out after 5 seconds.
  • UCM is only called when CDC reports zero total warnings, zero total errors and status 0.
  • OVERRIDE_VALIDATION (contact-level or per address) suppresses warnings, never errors.
  • Totals include address warnings and errors only when the contact itself has some; address-only issues are not counted. This may be a defect.
  • Validation and UCM rejections are normal replies with a non-zero status, not technical errors.
  • If CDC returns status 0 with warnings, the caller gets 'General Un-Attribute Error' with no validation details. This may be a defect.
  • Address language is hard-coded 'nl' and street-naming convention 'PROPRIETARY' on the way to CDC.
  • Reply header uses ID 1048 and PARADIGM 'REQUEST', unlike the request's 1046; replicate unless the client agrees to change it.

Complexity

  • Validation totals with sum() over addresses and override flags matched by position (Groovy map function)
  • Post-processing needs the original request alongside the CDC response (Document Cache)
  • Large but mostly 1:1 ContactPerson mappings (five)
  • Header and status schemas missing

  • Transport for reaching CDCAdapter and UCMAdapter (shared decision with crm-shared-framework).
  • Base.xsd and ResultStatus.xsd are needed for the six profiles.

Client questions

Which applications call UpsertContact today, and can they move from TIBCO Rendezvous to EMS request/reply or to an HTTP API?

Identify the callers of UpsertContact and confirm they can move from RV request/reply to EMS request/reply (or HTTP). This decides whether the listener and reply are JMS or a Web Services Server listener.

If this is not answered: Callers move to an EMS request queue named like today's subject (<Env>.FIXED.CRM.CRMServices.Request.UpsertContact.1), with the same decision as GetAccountData.

Should warnings or errors reported only on a contact's addresses (with none on the person) stop the contact from being saved in UCM?

As written, the totals are computed only when the contact-level warning or error count is above 0, so warnings or errors reported only on addresses produce totals of 0 and the contact is upserted. Confirm whether this is intended behaviour to replicate or a defect to fix.

If this is not answered: Today's behaviour is replicated exactly: address-only findings do not stop the upsert.

When a contact is marked 'override validation', should the override also stop contact-level warnings from counting towards the total that blocks the save?

Also, the contact-level override is applied to VALIDATION_WARNING_COUNT, but the totals test reads the raw response counts, so an overridden contact warning can still block the save.

If this is not answered: Today's behaviour is replicated: totals use the raw counts.

When validation stops a contact but the validation service reports success status, should the caller receive the validation details instead of the generic 'General Un-Attribute Error' with no details that it gets today?

In this case the reply has no BODY, so the caller cannot see which warning or error stopped the contact. This looks like a defect, and the fix changes the reply content.

If this is not answered: Today's reply is replicated exactly: STATUS 1, 'General Un-Attribute Error', no BODY.

Does the validation service always return a contact's addresses in the same order as they were sent?

The override uses the request ADDRESS at the same position as the response ADDRESS. If the order can change, the override applies to the wrong address.

If this is not answered: Order is preserved, and addresses are matched by position as today.

Should every address still be sent for validation as Dutch-language with the 'proprietary' street-naming convention, whatever the caller supplied?

Language 'nl' and naming convention 'PROPRIETARY' are hard-coded, which overrides any convention the caller sends. Foreign addresses may be validated incorrectly.

If this is not answered: The hard-coded values are kept.

Which system sits behind the CDC validation service, and who owns it?

The system behind CDCAdapter and its owner are not named in the export. The transport choice and testing need a contact.

If this is not answered: CDCAdapter is reached the same way as UCMAdapter (the shared transport decision), with no change to its message format.

Do any callers depend on the reply header fields as they are today (reply ID 1048 with type 'REQUEST'), or may they be corrected to a response type?

The reply header identifies itself as service 1048 with PARADIGM 'REQUEST', and the UCM request is labelled 'ValidateContact'. Correcting these could affect callers' parsing or monitoring.

If this is not answered: Header values are reproduced exactly as today.

How long do callers wait for an UpsertContact reply, and how many requests per day and per peak hour are expected?

The service makes two back-end calls in sequence, each allowed 5 seconds. Any extra hop from the new transport must fit within the callers' timeout, and volumes drive sizing.

If this is not answered: Callers wait at least 15 seconds; low volume; low-latency mode on a single runtime.

The process

The caller sends an UpsertContactRequest containing one CONTACT_PERSON: names, date of birth, contact media, addresses, Siebel account references and override flags. CRMServices validates the request against the schema, builds a ValidateContactRequest for CDCAdapter (marking addresses as Dutch-language with a proprietary street-naming convention and defaulting missing address overrides to false) and calls CDC. The CDC response is post-processed: override flags from the request force the matching warning counts to zero, and total warning and error counts are calculated. If the totals are both zero and CDC's status is 0, the validated contact is sent to UCMAdapter as an UpsertContactRequest. If UCM returns status 0, the caller receives status 0 'No Error' with the contact data returned by UCM. Otherwise the caller receives the CDC or UCM status and details. Technical failures return status 1 with message code CRMS-03011 or CRMS-03000, and those after a successful parse also send an error mail.

User stories

US-001 Upsert a validated contact High

Role: Front-end CRM consumer

As a CRM consumer I want to submit a contact person so that it is validated and stored in UCM, and I am told about any validation problems.

  • When CDC reports no warnings or errors and status 0, the contact is sent to UCM and the reply has STATUS '0', 'No Error' and the contact data returned by UCM.
  • When CDC reports warnings or errors, UCM is not called. If CDC status != 0, the reply carries CDC's RESULT_STATUS and validation details. If CDC status = 0, the reply is STATUS 1 'General Un-Attribute Error' with no BODY (current behaviour; see questions).
  • When UCM returns STATUS != 0, the reply carries UCM's RESULT_STATUS and BODY.
  • The reply's MESSAGE_ID equals the request's MESSAGE_ID.

Role: Front-end CRM user

As a CRM user I want to confirm a contact or address despite validation warnings so that a correct but unusual record can still be stored.

  • ADDRESS[n]/OVERRIDE_VALIDATION = 'true' sets the warning count of the n-th returned address to 0.

Error handling

Strategy
Business rejections (CDC or UCM) are normal replies with a non-zero RESULT_STATUS. Technical failures in the sub-processes raise an Errors fault, copying the requester error or CRMS-03000. Main_UpsertContact mails, then throws an ErrorReply with a ready-made response body, and the starter replies with it. In Boomi: decisions for business outcomes; Try/Catch for technical errors; error mail via crm-shared-framework; error reply in the Catch path.
Retries
None; the synchronous caller decides.
Compensation
None. If UCM is updated and the reply then fails, the update stands.

Process flow

Step by step

  1. Receive UpsertContact request — BW: RV ...Request.UpsertContact.1. Boomi (assumed): uc-listen-op.
  2. Parse and validate request — 0426 UpsertContactRequest; cache the request in the Document Cache.
  3. Map to CDC request — uc-req-to-cdc-map; language 'nl', PROPRIETARY.
  4. Build parse-error reply — STATUS 1 'Technical Error'; CRMS-03011; no mail.
  5. Call CDC ValidateContact — Timeout 5000 ms.
  6. Apply overrides and totals — uc-cdc-postprocess-map + uc-validation-totals-fn.
  7. Validation clean? — TOTAL_WARNING = 0 and TOTAL_ERROR = 0 and STATUS = 0.
  8. Map to UCM request — uc-cdc-to-ucm-map.
  9. Call UCM UpsertContact — Timeout 5000 ms.
  10. UCM status = 0?
  11. Send error mail — Sub: CRM Send Error Mail (crm-shared-framework).
  12. Map success response — STATUS 0 'No Error' + UCM CONTACT_PERSON.
  13. Map business error response — uc-error-response-map: CDC or UCM status and BODY.
  14. Build technical-error reply — STATUS 1 'General Un-Attribute Error'.
  15. Send reply — uc-reply-op.
  16. Log error, no reply — When the reply fails.

How it is built today

Five BW processes. Reply_UpsertContactRV is the RV starter (trace, reply, error reply). Main_UpsertContact parses and validates, rebuilds the header, builds error replies and sends the error mail. Sub_UpsertContact_UpsertContact maps to CDC, decides on the validation counts, maps to UCM, decides on UCM status and builds the response or the business error response. _Sub_ValidateContact makes the CDC request/reply call and applies overrides and totals. _sub_UpsertContact makes the UCM request/reply call. Both back-end calls go through Common Sub_Requester over Rendezvous.

How it should be built in Boomi

One Boomi listener process, 'CRM Contact UPSERT Listener' (uc-main-process), in folder CRMServices/UpsertContact, running in low-latency mode with simultaneous executions allowed. Listen, then Set Properties (DPP_MessageId, reply destination, correlation ID), then Document Cache add of the request, then Try. Inside the Try: map to CDC, the CDC connector, the post-process map, a Decision, then (if clean) map to UCM, the UCM connector, a Decision, and the success or business-error map. The reply goes through uc-reply-op. Catch: a Decision on error type, Process Call to the error mail (crm-shared-framework) except for parse errors, the technical-error map, then reply. Shared EMS connection, CMH function and error handler come from crm-shared-framework.
