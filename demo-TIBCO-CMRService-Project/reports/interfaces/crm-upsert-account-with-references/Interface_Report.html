Purpose

Consumes an account-hierarchy publication (KPN EAI service 1056, contract 0420 'UpsertAccountWithReferencing') and writes every account of the hierarchy to SFA, one account at a time (SFAAdapter UpsertAccount, contract 0421). For each account and contact that SFA reports as newly created, it registers the external references in UCM (AddAccountReference 0422, via crm-shared-framework). Hierarchies of more than 50 accounts are rejected. Accounts are processed sequentially by republishing the remaining list to a private queue after each account.

Business context

It is the second half of the account synchronisation that GetAccountData (crm-getaccountdata-rv) starts: GetAccountData reads the hierarchy from UCM and publishes it, and this interface applies it to SFA and records the resulting cross-references back in UCM. The publication arrives through an EMS topic-to-queue bridge. Other producers may also publish to the same topic: the Residential filter only matters for publications not marked RecursiveProcessing = true, and GetAccountData always sets it to true. No other producer is visible in the export.

Summary

This interface takes a customer's account hierarchy, published by GetAccountData, and writes it into SFA. It flattens the tree into a list, refuses anything over 50 accounts, and then handles the accounts strictly one at a time. For each account it calls SFA's 'upsert account'. For every account and contact that SFA reports as newly created, it asks UCM to record the external reference, so that both systems know the same customer by the same identifiers.

The one-at-a-time processing is done in an unusual way. After each account, the remaining list is put back on a private message queue and picked up again. That makes each account its own unit of work, but if one account fails, all accounts after it in that hierarchy are abandoned. The failing list is sent to integration support by e-mail and to the exception queue. There is no rollback: an account already written to SFA stays written, even if its UCM references fail.

This is the most complex interface in the project. It combines a tree-flattening step that needs a script, a choice about whether to keep the private-queue iteration in Boomi, a filtering rule for residential accounts, nested loops over accounts and contacts, and writes to two systems with no compensation. It also shares the project-wide blockers: Rendezvous transport to the adapters, missing header schemas, and the missing exception handler.

Key points

  • Rejects hierarchies over 50 accounts (CRMS-03001). This goes only to the exception framework; no e-mail is sent at that stage.
  • Accounts are processed one per message, parents before children (document order of the flattened tree).
  • Residential filter: unless RecursiveProcessing = true, a Residential account is sent only if it has an SFA CifAccountReference. GetAccountData always sets RecursiveProcessing = true.
  • SFA receives the account, its affiliations, contacts and business addresses, but not its CifAccountReference list.
  • UCM references are added only for accounts and contacts SFA marks OCRMOperation = 'Create'.
  • A failure stops the rest of that hierarchy; there is no compensation, so SFA and UCM can be left partially updated.
  • An empty account list is logged (CRMS-03022) and ignored.
  • When an account is skipped by the Residential filter, the message carried to the next iteration loses its tracking information (MESSAGE_ID). This looks like a defect.

Client questions

If one account in a hierarchy fails, should the migrated process be able to restart from that account, or is it acceptable to re-run the whole hierarchy?

Decide whether to keep the self-republishing internal queue (durable per-account checkpoint; each account is its own Boomi execution) or replace it with an in-process split of the flat list and sequential processing in one execution. This changes how many processes and queues are built.

If this is not answered: In-process sequential processing in one execution; on failure, the remaining accounts (including the failed one) are sent to the exception queue and the error mail, so they can be re-driven.

Is it safe to send the same account to SFA, and the same external reference to UCM, a second time when a failed hierarchy is re-processed?

Confirm that SFA UpsertAccount is idempotent (it is an upsert) and that re-adding an existing UCM reference is harmless or rejected predictably. Without that, the re-drive procedure is unsafe, because SFA and UCM are updated in sequence with no rollback.

If this is not answered: Both operations are treated as safe to repeat, and re-drive re-sends the failed account in full.

Apart from GetAccountData, which systems publish account hierarchies to this flow, and should their residential accounts still be skipped unless they already have an SFA reference?

Confirm the business meaning of the Residential filter. All publications from GetAccountData set RecursiveProcessing = true, so the filter only applies to publications from other producers, and none are visible in the export.

If this is not answered: The filter is kept exactly as today.

Should a hierarchy with more than 50 accounts still be rejected completely, and should integration support be e-mailed when that happens?

Today such hierarchies are rejected (CRMS-03001) and only recorded in the exception framework, with no e-mail. A large customer can therefore silently fail to synchronise.

If this is not answered: The 50-account limit is kept, and rejection is recorded in the exception framework without e-mail, as today.

After a residential account is skipped, should the remaining accounts keep the original message tracking ID, which today is lost from that point on?

When an account is skipped by the filter, the message passed to the next iteration has no tracking information, so later logs and exception records cannot be tied to the original request, and processing may fail.

If this is not answered: The original tracking ID is kept for all accounts (fixing the defect).

When a hierarchy fails, should the error e-mail still list all remaining accounts with their contacts' personal details?

The mail body today contains the full remaining account list, including names, birth dates, e-mail addresses and phone numbers of contacts.

If this is not answered: The e-mail carries the message ID, error and failing account ID only; the full list goes to the exception queue.

After a failure is recorded, should the failed publication ever be retried automatically, or only re-driven by support?

Today every message is acknowledged after the error is handed to the exception framework. Whether that framework re-queues it is not in the export.

If this is not answered: No automatic retry; support re-drives from the exception record.

How many hierarchy publications arrive per day, and how many accounts does a typical hierarchy contain?

Each account costs one SFA call plus one UCM call per new reference, each allowed 5 seconds, so volumes decide whether sequential processing in one run is fast enough.

If this is not answered: Low volume; typical hierarchies of fewer than 10 accounts.

The process

A hierarchy publication arrives on the Subscribe queue. It is parsed as UpsertAccountWithReferencingPublish and flattened: every SiebelAccount at any depth, in document order, becomes an entry of FlatAccountHierarchy with its affiliations, contacts, business addresses and CIF account references, and the RecursiveProcessing flag is carried over. If the flat list has more than 50 accounts, the publication is rejected with CRMS-03001. Otherwise the flat list is sent to the private queue _UpsertAccountWithReferences.1. The worker listener takes the list and looks only at the first account. If RecursiveProcessing = 'true', or the first account's Type is not 'Residential', the account is upserted into SFA. A Residential account in a non-recursive publication is upserted only if it has a CifAccountReference with SystemName 'SFA'. The upsert sends the account to SFA; if SFA reports success, each CifAccountReference of an account SFA created, and each CifContactReference of a contact SFA created, is registered in UCM. The first account is then removed and, if any remain, the shortened list is republished to the same private queue for the next iteration. Any failure stops the iteration, sends an error e-mail containing the remaining list, and passes the error to the exception framework.

User stories

US-001 Write an account hierarchy to SFA and UCM High

Role: CRM operations

As CRM operations I want each account in a published hierarchy written to SFA, with new cross-references registered in UCM, so that both systems share the same account identities.

  • Hierarchies of more than 50 accounts are rejected with CRMS-03001 and no account is written.
  • Each account is sent to SFA UpsertAccount once, in document order of the flattened tree (parents before children).
  • For every account and contact that SFA reports with OCRMOperation 'Create', each external reference is registered via UCM AddAccountReference.
  • Accounts and contacts not created by SFA get no AddAccountReference call.

US-002 Do not synchronise unlinked residential accounts Medium

Role: CRM data owner

As the CRM data owner I want residential accounts from non-recursive publications sent to SFA only when they already have an SFA reference, so that SFA is not filled with residential customers it does not manage.

  • RecursiveProcessing = 'true': every account is sent.
  • Otherwise, a non-Residential account is sent.
  • Otherwise, a Residential account is sent only if it has a CifAccountReference with SystemName 'SFA'.
  • A skipped account does not stop processing of the following accounts.

Error handling

Strategy
Errors are raised as KPN Errors (CRMS-03001, CRMS-03021, requester errors, CRMS-03000) and propagate to the listener, which calls Common Sub_ThrowException and then acknowledges. The worker additionally mails the remaining list before throwing. In Boomi: Try/Catch per listener; Catch calls 'Sub: CRM Send Error Mail' (worker only) and 'Sub: CRM Error Handler' with the remaining list, then ends normally so the message is acknowledged.
Retries
None in this interface: no redelivery flag is computed and the message is always acknowledged. Whether Common Sub_ThrowException triggers redelivery is not in the export.
Compensation
None. SFA writes and earlier UCM references are not undone. Re-driving the remaining list re-sends the failed account to SFA (an upsert) and its references to UCM.

Process flow

Step by step

  1. Receive hierarchy publication — Queue ...Subscribe.UpsertAccountWithReferences.1 (uawr-subscribe-listen-op).
  2. Parse publication — UpsertAccountWithReferencingPublish.
  3. Flatten hierarchy — uawr-flatten-fn; descendant order.
  4. More than 50 accounts?
  5. Reject CRMS-03001 — Exception framework; acknowledge; no mail.
  6. Send list to internal queue — uawr-internal-send-op.
  7. Acknowledge publication
  8. Receive flat list (worker) — uawr-internal-listen-op.
  9. Any accounts left? — count(SiebelAccount) > 0; else trace CRMS-03022.
  10. Recursive or non-Residential? — RecursiveProcessing = 'true' or Type != 'Residential'.
  11. Has SFA reference? — CifAccountReference[SystemName = 'SFA'].
  12. Upsert account in SFA — uawr-sfa-upsertaccount-op; STATUS != 0 is an error.
  13. Add account references in UCM — Created accounts only; Sub: UCM AccountReference ADD.
  14. Add contact references in UCM — Created contacts only.
  15. Remove processed account — uawr-remaining-accounts-map.
  16. Remainder not empty?
  17. Republish remainder — Back to the internal queue.
  18. Mail and exception record — 'Error in UpserAccountWithReferencing' + Sub: CRM Error Handler; remaining accounts abandoned.
  19. Iteration done — Acknowledge.

How it is built today

Two JMS listeners and six processes. Subscribe_UpsertAccountWithReferencesJMS calls Main_UpsertAccountWithReferences (parse), which calls Sub_UpserAccountWithReferencing (flatten, 50-account check, send to the internal queue). _Subscribe_UpsertAccountWithReferencesJMS calls _Sub_UpsertAccountWithReferences (parse, error mail, throw), which calls _Sub_UpsertAccountWithReferencing_RecursivePublish (filter, upsert, remove, republish). That calls _Sub_UpsertAccountIntoSFA_UCM (SFA upsert via Sub_UpsertAccount, then UCM AddAccountReference loops via Sub_AddAccountReference). Iteration over accounts is achieved by the worker republishing to its own queue. Failures in both listeners go to Common Sub_ThrowException, and the message is then acknowledged.

How it should be built in Boomi

Recommended: one Boomi listener process, 'CRM UpsertAccountWithReferences Listener' (uawr-main-process), in folder CRMServices/UpsertAccountWithReferences. Shapes: listen, Groovy flatten (one document per account), a Decision on count > 50, then Flow Control (1 thread, sequential) with a per-account Decision chain for the Residential filter. Each account goes through Process Call 'Sub: CRM Account UPSERT Into SFA and UCM', inside a Try/Catch that stops at the first failure and passes the remaining accounts to the error handler and mail. If per-account durability is required, keep the two-process design instead: the listener sends to the internal queue, and 'CRM UpsertAccountWithReferences Account Worker' (uawr-worker-process) processes one account and republishes the remainder. The shared EMS connection, AddAccountReference sub-process, error mail and error handler come from crm-shared-framework.
