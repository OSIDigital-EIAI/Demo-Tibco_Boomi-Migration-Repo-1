Purpose

A synchronous request/reply service (KPN EAI service 1054 'GetAccountData', contract 0418). Given a Siebel account ID, it retrieves the account's complete hierarchy from UCM through UCMAdapter (GetAccountHierarchy, service 0419) and publishes that hierarchy as an 'UpsertAccountWithReferencing' event (contract 0420). That event triggers the account to be written to SFA and its references registered in UCM. The caller receives only a status: the account data itself is not returned.

Business context

It exists so that a front-end CRM consumer can trigger a full synchronisation of a customer's account hierarchy from the customer master (UCM) to the sales system (SFA). The UpsertAccountWithReferences interface (crm-upsert-account-with-references) depends on the event it publishes. The callers of the service are not identified in the export. The adapter names and the 'SiebelAccount' and 'UCMRowId' content suggest that UCM and SFA are Siebel applications, but the export does not state this.

Summary

GetAccountData is the starting point of the account synchronisation. A calling application sends a Siebel account ID. CRMServices asks UCM, through UCMAdapter, for the account's whole hierarchy (the account, its child accounts at any depth, their contacts, affiliations and business addresses), converts it into the CRMServices publication format, and publishes it on the message bus for the UpsertAccountWithReferences flow to process. The caller receives a reply that reflects UCM's status: success, or UCM's error code and description.

If UCM reports an error, nothing is published and the caller receives UCM's error. A technical failure (bad request, timeout, publishing error) produces a 'Technical Error' reply and an e-mail to integration support.

Three things make this interface complex to move to Boomi. The service and its call to UCM both run over TIBCO Rendezvous, which Boomi cannot connect to, so a transport decision is needed first. The account hierarchy is recursive (accounts contain accounts) and must be converted by a script, because Boomi maps cannot recurse. And the message header and status schemas, plus the helper code that reads message IDs, are in a TIBCO library that was not exported.

Key points

  • Returns a status only; the account data is published as an event, not returned to the caller.
  • Publishes only when UCM returns status 0; a UCM error is returned to the caller and also e-mailed.
  • The published hierarchy always has RecursiveProcessing = true, which disables the Residential filter downstream.
  • No size check: hierarchies above 50 accounts are published here and rejected later by UpsertAccountWithReferences (CRMS-03001).
  • Inbound and UCM calls use TIBCO Rendezvous; Boomi has no Rendezvous connector.
  • Recursive account-tree conversion needs a Groovy script.
  • The publication does not carry CifAccountReference or OCRMOperation; the UCM response type has neither.

Client questions

Which applications call GetAccountData today, and can they move from TIBCO Rendezvous to EMS request/reply or to an HTTP API?

Identify the GetAccountData callers and confirm the target inbound transport (EMS request/reply or Boomi API). Boomi cannot receive Rendezvous requests, so the listener and reply cannot be built until this is decided.

If this is not answered: Callers move to an EMS request queue named like today's subject (<Env>.FIXED.CRM.CRMServices.Request.GetAccountData.1) and receive the reply on their JMSReplyTo destination.

How long do callers wait for a GetAccountData reply before giving up, and how many requests per day and per peak hour should we expect?

The service makes a call to UCM (up to 5 seconds) and a publish before replying. Any extra hop added by the new transport must fit inside the callers' timeout, and volumes drive runtime sizing.

If this is not answered: Callers wait at least 10 seconds; volume is low (thousands per day or fewer); the service runs in low-latency mode on a single runtime.

What is the largest account hierarchy (number of accounts and number of levels) that UCM can return for one customer?

Confirm the maximum realistic hierarchy depth and size. The conversion handles any depth, but hierarchies of more than 50 accounts are published here and then rejected by the UpsertAccountWithReferences flow.

If this is not answered: No depth limit is enforced here; a safety limit of 20 levels raises an explicit error; the 50-account limit stays downstream as today.

Should GetAccountData reject hierarchies of more than 50 accounts immediately, instead of publishing them for the UpsertAccountWithReferences flow to reject later?

Decide whether to reject them earlier (in GetAccountData) or keep the current behaviour. Today the caller is told the request succeeded even though the synchronisation is later rejected with CRMS-03001.

If this is not answered: Current behaviour is kept: publish regardless of size; the limit is enforced downstream.

Must the publish of the account hierarchy still happen before the caller receives its reply, so that a failed publish is reported to the caller as an error?

In BW the publish happens before the reply, inside the same job. If the publish fails, the caller gets an error reply. If the reply fails after a successful publish, the synchronisation still happens. Confirm whether the Boomi build must keep 'publish, then reply' ordering.

If this is not answered: The order is kept: publish first, then reply.

Do any callers depend on the exact content of error replies, such as the empty version field or the event name 'GetAccountDateRespone' (misspelt), or may these be corrected?

Confirm whether consumers depend on the empty CMH/VERSION and the misspelt EVENT 'GetAccountDateRespone' in error replies, or whether the Boomi build may normalise them.

If this is not answered: Error replies are reproduced exactly, including the empty version and the misspelling.

When UCM reports an error for an account (for example, account not found), should integration support still receive an error e-mail, as happens today?

Today any UCM error, including business errors, sends an 'Error in GetAccountData' e-mail as well as returning the error to the caller. This may produce e-mails for routine 'not found' cases.

If this is not answered: Current behaviour is kept: every UCM error sends an e-mail.

Should empty 'DisableMailings' and 'MasterAccountIntegrationId' fields still be sent in the published hierarchy when UCM does not supply them?

Today these two fields are always written, even when empty, while every other optional field is omitted when absent. The consumer may treat an empty value differently from a missing one.

If this is not answered: The current behaviour is reproduced: both fields are always written.

Which access control should protect GetAccountData once it is no longer on the Rendezvous network (for example EMS queue permissions or API credentials)?

Today no caller authentication exists in the service; access relied on network and Rendezvous subject segregation.

If this is not answered: EMS queue permissions restrict who can send to the request queue; no message-level authentication is added.

The process

On receipt of a GetAccountDataRequest (CMH header plus BODY/SIEBEL_ACCOUNT_ID), CRMServices validates the request against the schema, then sends a GetAccountHierarchyRequest to UCMAdapter with the same account ID and tracking information. If UCM answers with STATUS_RESULT/@STATUS = 0, every SiebelAccount in the response is converted recursively into the publication format. The resulting UpsertAccountWithReferencingPublish (RecursiveProcessing = true) is published to the EMS topic, and the caller receives a GetAccountDataResponse whose STATUS_RESULT is UCM's. If UCM answers with a non-zero status, nothing is published: an error mail is sent and the caller receives an error reply carrying UCM's status. Technical failures produce a 'Technical Error' reply with message code CRMS-03011 or CRMS-03000, plus an error mail.

User stories

US-001 Trigger account-hierarchy synchronisation High

Role: Front-end CRM consumer

As a CRM consumer I want to request GetAccountData for a Siebel account ID so that the account and its whole hierarchy are synchronised from UCM into SFA.

  • A valid request with SIEBEL_ACCOUNT_ID receives a GetAccountDataResponse whose STATUS_RESULT mirrors UCM's status.
  • On UCM STATUS = 0, exactly one UpsertAccountWithReferencingPublish message with RecursiveProcessing = true is published, containing every account of the hierarchy at every depth.
  • On UCM STATUS != 0, nothing is published and the caller receives UCM's ERROR_CODE/ERROR_DESCRIPTION.
  • An unparseable request receives STATUS 1, ERROR_CODE '1', 'Technical Error' and MSG_CODE CRMS-03011.
  • A failure triggers an error mail 'Error in GetAccountData'.

legacy/tibco/CRMServices/CRMServices/Processes/Main_GetAccountdata.process

US-002 Preserve the full account tree High

Role: CRM data owner

As the CRM data owner I want every child account, contact, affiliation and business address in the UCM hierarchy carried into the publication so that nothing is lost on the way to SFA.

  • The publication has the same tree shape and account count as the UCM response.
  • Optional account fields are present only when UCM supplied them; DisableMailings and MasterAccountIntegrationId are always present.
  • Contact, affiliation and business-address fields are copied for every occurrence.

Error handling

Strategy
Layered BW error transitions. Sub_GetAccountHierarchy and Sub_GetAccountdata raise Errors or ResultStatus faults. Main_GetAccountdata sends an error mail and throws an ErrorReply containing a ready-made error response body. Reply_GetAccountdataRV logs and replies with that body. In Boomi: one Try/Catch around the implementation, a Decision on error type, error mail via crm-shared-framework, then the error reply.
Retries
None. A synchronous caller decides whether to retry.
Compensation
None. If the reply fails after a successful publish, the synchronisation still proceeds.

Step by step

  1. Receive GetAccountData request — BW: RV subject ...Request.GetAccountData.1. Boomi (assumed): JMS listener gad-listen-op.
  2. Parse and validate request — GetAccountDataRequest, schema-validated.
  3. Map to UCM request — gad-req-to-ucm-map; CMH ID 1054.
  4. Build parse-error reply — CRMS-03011, STATUS 1 'Technical Error'; no mail.
  5. Call UCM GetAccountHierarchy — Request/reply, timeout 5000 ms.
  6. UCM status = 0? — STATUS_RESULT/@STATUS.
  7. Convert hierarchy recursively — gad-hierarchy-recursive-fn (Groovy).
  8. Publish UpsertAccountWithReferencing — EMS topic ...Publish.UpsertAccountWithReferences.1; RecursiveProcessing = true.
  9. Map success response — gad-ucm-to-response-map.

  11. Build error reply — gad-error-response-map; ResultStatus copied or 'General Un-Attributable error'.
  12. Send reply — gad-reply-op to the caller's reply destination.
  13. Log error, no reply — When no error body exists or the reply fails.

How it is built today

Four BW layers. Reply_GetAccountdataRV is the RV starter: trace, reply and error reply. Main_GetAccountdata parses and validates the request, builds error replies and sends the error mail. Sub_GetAccountdata orchestrates the UCM call, the status check, the recursive conversion loop and the publish. Sub_GetAccountHierarchy makes the request/reply call via Common Sub_Requester and parses the reply. The tree conversion uses SiebelAccountMapper.1 and .2 calling each other. Publishing uses Common Sub_Publisher. Logging and error trace use Common Sub_Trace and Sub_ErrorTrace, gated by the custom Java eai:isTraceOn.

How it should be built in Boomi

One Boomi listener process, 'CRM AccountData GET Listener' (gad-main-process), in folder CRMServices/GetAccountData, running in low-latency mode with simultaneous executions allowed. Shapes: JMS listen (gad-listen-op), then Set Properties (DPP_MessageId, reply destination, correlation ID), then Try. Inside the Try: map to the UCM request, the UCM request/reply connector, a Decision on STATUS, the Groovy recursive conversion, the EMS publish, the success map and the JMS reply. Catch: a Decision on error type, Process Call to 'Sub: CRM Send Error Mail' (crm-shared-framework) except for parse errors, the error-response map, then the JMS reply. Shared EMS connection and CMH function come from crm-shared-framework.
