Executive summary

The export is a TIBCO BusinessWorks 5.x project named 'CRMServices' (component version 2.0.3, authored by 'KPN EAI', last designed in TIBCO Designer 5.5.0.1 and held in ClearCase). It is a customer-data integration hub that sits between callers and three back-end adapters: UCMAdapter, SFAAdapter and CDCAdapter. Judging by the message content (SiebelAccount, UCMRowId, 'Siebel Hierarchical' integration objects), the first two front Siebel UCM (customer master) and Siebel SFA (sales). CDCAdapter provides contact validation; the system behind it is not named in the export. It offers two synchronous request/reply services (GetAccountData and UpsertContact) and two asynchronous, event-driven flows (UpsertAccountWithReferences and UpsertContactPub).

The deployment descriptor (CRMServices.archive) deploys seven starter processes. They form four business interfaces: (1) GetAccountData reads an account hierarchy from UCM and republishes it as an event; (2) UpsertContact validates a contact with CDC and writes it to UCM; (3) UpsertAccountWithReferences takes that hierarchy event, flattens it, rejects hierarchies of more than 50 accounts, and writes each account to SFA and its cross-references to UCM, one account at a time; (4) UpsertContactPub takes a contact event, writes it to SFA and, for newly created contacts, registers the SFA reference in UCM. A fifth start-up process only registers the component with the in-house EAI framework.

The export is incomplete in ways that matter. The project depends on a shared library, Common_2.2.2.projlib, that is not included. That library holds the transport sub-processes (request/reply, publish, JMS send), the error, trace and exception framework, the JMS and Rendezvous connection definitions, and the common message-header schemas (Base.xsd, ResultStatus.xsd, Errors.xsd) that every message imports. The custom Java functions used for message IDs and trace switching, and the mail settings, are also missing. These gaps do not stop the analysis, but they must be closed before profiles and connections can be built.

The main migration challenge is transport. Both synchronous services and every back-end call use TIBCO Rendezvous (RV), and Boomi has no Rendezvous connector. The event flows use TIBCO EMS (JMS), which Boomi supports through its JMS connector. Recursive account-hierarchy mapping, queue-based iteration with redelivery-count retry, and multi-system writes with no rollback also need deliberate design decisions. Overall complexity is high for the two account interfaces and medium for the two contact interfaces.

Key findings

  • Platform is TIBCO BusinessWorks 5.x (Designer 5.5.0.1, process palette 5.4.0): .process files, CRMServices.archive, defaultVars/*.substvar and AESchemas. It is not BW6 or BWCE.
  • CRMServices.archive deploys 7 starters: Start_CRMServices, Reply_GetAccountdataRV, Reply_UpsertContactRV, Subscribe_UpsertAccountWithReferencesJMS, _Subscribe_UpsertAccountWithReferencesJMS, Subscribe_UpsertContactPub, _Subscribe_UpsertContactPub, plus /Common/Sub Processes/Sub_CommonBundle.process from the missing Common library.
  • The Common project library (Common_2.2.2.projlib, declared in .designtimelibs) is not in the export. It supplies Sub_Requester, Sub_Publisher, Sub_NotifierJMS, Sub_Trace, Sub_ErrorTrace, Sub_ThrowException, Sub_RegisterComponent, 'JMS Connection.sharedjmscon', 'RVCMQ Transport.rvtransport', EAIMessages.xml and the Base.xsd / ResultStatus.xsd / Errors.xsd schemas.
  • Both request/reply services listen on TIBCO Rendezvous certified-message queue subjects (%%Env%%.FIXED.CRM.CRMServices.Request.GetAccountData.1 and ...Request.UpsertContact.1). Boomi has no Rendezvous connector.
  • All six back-end calls go through Common Sub_Requester with a 5000 ms timeout (CRMServices/RV/Timeout). The test stubs answer on RV subjects such as %%Env%%.FIXED.CRM.UCMAdapter.Request.AddAccountReference.1, which shows the back-end adapters are reached over Rendezvous.
  • Custom Java XPath functions (namespace java://com.kpn.eai.component.common.CommonXPathFunctions: getMessageId, isTraceOn, getMessageText) are used in 33 places. No Java source or JAR is in the export.
  • GetAccountData does not return account data. It returns only a status, and as a side effect publishes the full UCM account hierarchy to the EMS topic %%Env%%.FIXED.Operations.CRMServices.Publish.UpsertAccountWithReferences.1.
  • The account hierarchy is recursive (SiebelAccount contains SiebelAccount). BW handles it with two mutually-recursive mapper processes (SiebelAccountMapper.1/.2) and a descendant-axis flatten (//SiebelAccount).
  • UpsertAccountWithReferences iterates by republishing the remaining accounts to its own internal queue, one account per message. Hierarchies with more than 50 accounts are rejected with CRMS-03001.
  • Writes to SFA and UCM are sequential and not transactional. No compensation logic exists in the source.
  • UpsertContactPub retries only timeout-class failures (EAI-03004, BWENGINE-100067, ERROR_CODE 10000) through JMS redelivery, up to 4 times for the SFA call and 5 times for the UCM AddAccountReference call. Other failures are mailed and the message is consumed.
  • The 'Publish.*' destinations are EMS topics, while the subscribers listen on 'Subscribe.*' queues. The topic-to-queue bridges are EMS server configuration and are not in the export.
  • The mail settings substvar (defaultVars/CRMServices/Mail/defaultVars.substvar) is listed in ClearCase metadata but is missing from the export, so the SMTP host and recipients are unknown.
  • The Common/JDBC global variables (Oracle host hdxs6k.telecom.ptt.nl, port 1526, SID D511) are not referenced by any process in this project and need no Boomi Database connection.
  • Not deployed and not to be migrated: 37 test processes under 'Test Processes', the orphan sub-process _Sub_UpsertAccountPub.process (no callers), the unused 0423_ValidateAddress schemas and RemoveEmptyTags.xslt (not referenced).

Integration flow

Source
CRM front-end consumers (RV request/reply callers, not identified in export) and UCM / upstream publishers (EMS topics Publish.UpsertAccountWithReferences.1 and Publish.UpsertContactPub.1)
Platform
TIBCO BusinessWorks 5.x engine 'CRMServices' with TIBCO Rendezvous (RVCM) and TIBCO EMS, plus the in-house KPN EAI Common framework
Target
UCMAdapter (Siebel UCM: GetAccountHierarchy, UpsertContact, AddAccountReference), SFAAdapter (Siebel SFA: UpsertAccount, UpsertContact), CDCAdapter (ValidateContact), SMTP mail, EAI exception queue

GetAccountData (RV) reads the account hierarchy from UCM and publishes it to an EMS topic. An EMS bridge delivers it to the UpsertAccountWithReferences queue, where the hierarchy is flattened and processed one account at a time (SFA UpsertAccount followed by UCM AddAccountReference for new references) by republishing to an internal queue. UpsertContact (RV) validates a contact via CDC and upserts it in UCM, returning the result synchronously. UpsertContactPub (EMS) applies UCM contact publications to SFA and, for creations, queues a UCM AddAccountReference that a second internal listener executes with its own retry limit. All flows use the KPN CMH message header and report failures by e-mail and to the Common exception framework.

US-001 · Trigger account-hierarchy synchronisation High

As a CRM consumer I want to request GetAccountData for a Siebel account ID so that the account and its whole hierarchy are synchronised from UCM into SFA.

Role: Front-end CRM consumer

  • A valid request with SIEBEL_ACCOUNT_ID receives a GetAccountDataResponse whose STATUS_RESULT mirrors UCM's status.
  • On UCM STATUS = 0, exactly one UpsertAccountWithReferencingPublish message with RecursiveProcessing = true is published.
  • On UCM STATUS != 0, nothing is published and the caller receives UCM's ERROR_CODE/ERROR_DESCRIPTION.
  • An unparseable request receives STATUS 1, ERROR_CODE '1', 'Technical Error' and MSG_CODE CRMS-03011.
  • A failure triggers an error mail 'Error in GetAccountData'.

US-002 · Upsert a validated contact High

As a CRM consumer I want to submit a contact person so that it is validated by CDC and stored in UCM, and I am told about any validation problems.

Role: Front-end CRM consumer

  • When CDC reports no warnings or errors and status 0, the contact is sent to UCM and the reply has STATUS '0', 'No Error' and UCM's BODY.
  • When CDC reports warnings or errors, UCM is not called and the reply carries CDC's RESULT_STATUS and validation details.
  • OVERRIDE_VALIDATION = 'true' suppresses warnings (not errors) for the contact or the matching address.
  • When UCM returns STATUS != 0, the reply carries UCM's RESULT_STATUS.

US-003 · Write an account hierarchy to SFA and UCM High

As CRM operations I want each account in a published hierarchy written to SFA, with new cross-references registered in UCM, so that both systems share the same account identities.

Role: CRM operations

  • Hierarchies of more than 50 accounts are rejected with CRMS-03001 and no account is written.
  • Each account is sent to SFA UpsertAccount once, parents before children (document order).
  • Residential accounts from a non-recursive publication are written only when they hold an SFA CifAccountReference.
  • For every account and contact created in SFA, each external reference is registered via UCM AddAccountReference.
  • A failure on one account stops the remaining accounts of that hierarchy and sends 'Error in UpserAccountWithReferencing'.

US-004 · Propagate contact publications to SFA High

As CRM operations I want contact changes published by UCM to be applied in SFA, and newly created SFA contacts referenced back in UCM, so that contacts stay aligned.

Security

AspectDetail
Credentials in configurationCommon/JMS/defaultVars.substvar holds the EMS and JNDI passwords as TIBCO-obfuscated Password values, plus the account names. TIBCO obfuscation is reversible, so these files must be treated as secrets. They are not reproduced in this report. In Boomi they must be set as encrypted Environment Extensions per environment.
Default account namesThe default JMS and JNDI user names in the substvar look like a generic administrative account rather than a dedicated service account. Confirm that production uses a least-privilege service account on EMS.
Transport encryptionPlain tcp:// EMS and RV URLs are the defaults. An ssl://localhost:7243 URL is defined but not shown to be used. Whether production traffic is encrypted is unknown, and the Boomi JMS connection must match or improve on it.
Authentication of callersThe RV request/reply services perform no caller authentication or authorisation in the processes. Access control relied on network and RV subject segregation. Moving to JMS or HTTP needs an explicit decision (EMS queue ACLs, or Boomi API authentication).
Personal dataMessages carry contact personal data (names, DATE_OF_BIRTH, e-mail, telephone, address). Error mails embed the full rendered message (tib:render-xml of the request), which sends personal data by e-mail. Reconsider under GDPR, for example by masking or by sending only the MESSAGE_ID.
